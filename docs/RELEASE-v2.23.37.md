# Quick Achieve v2.23.37

## 一、配置损坏后恢复，会挑中"空备份"把你的设置救没

实测：把 `config.json` 写成半截乱码再启动 —— 程序正确地留档了坏文件（加密存档 `config.json.bad-1`），也确实从备份恢复了。但**恢复的是完整度 0 的那份**（等于出厂配置），而备份目录里还有完整度 55 的历史备份。

根因是 `looks_wiped()` 的**假阴性**：

- 它把 `c.bar_list != DEFAULT_BAR` 当成"用户定制过"的证据；
- 而迁移代码（`ensure_img_bar_sentinel` / `ensure_trans_bar_sentinel`）会往**任何**配置里补 `@img` / `@trans` —— **包括一份刚出厂的默认配置**；
- 于是"最新那份其实是默认配置"永远判不成"被清空"，恢复链直接拿它覆盖你的设置。

现在把 `@` 开头的哨兵剔掉再比（`bar_list_is_defaultish`）：只多了我们自己的哨兵 → 仍算默认 → 触发"回退到更早的正常备份"。

⚠ 没有改你定过的那条口径：**默认仍然恢复最新一份**，只有"疑似被清空"才往回找。新增单测钉住四件事：

```
出厂默认            → 算 wiped
补过哨兵            → 仍算 wiped（这次修的就是它）
真加了一颗引擎      → 不算
加了分隔线          → 不算
```

## 二、运行库"解出来就算就位"，但可能加载不了

模型下载那条链很扎实（`.part` → 多源 → 体积 → **SHA256** → 原子 rename）。
但**运行库**（onnxruntime）那条没法钉哈希（官方 zip 的 SHA256 没写在代码里），原来只验"体积 ≥ 20MB + 能解压"。

于是"体积对、内容坏"的 dll 会同时骗过 `runtime_ready()`（只比体积）和界面：显示"运行库已就位"，真要用 AI 抠图时才失败 —— 而你不会想到是文件坏了、要重下。

现在解压成功后**当场试加载一次**（`runtime_available()`，内部有 `catch_unwind`），加载不了就删掉、换下一个源 —— 绝不留一个"看着在、用不了"的文件。
