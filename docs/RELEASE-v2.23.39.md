# Quick Achieve v2.23.39

> 拿你机器上的真实日志逐段算耗时，改出来的两处。

## 一、精确复核对"注定失败"的窗口空等 700ms，还常等两遍

你的日志里超过 300ms 的操作只有一种，而且**成对**出现：

```
capture(exact): 700ms 内没读到新内容（目标 pid=67680 写没写=false）
capture(exact): 700ms 内没读到新内容（目标 pid=67680 写没写=false）
```

`写没写=false` = 这个窗口**根本没理会**我们模拟的 Ctrl+C。同一次取词复核两遍、两遍都注定失败 → 白等 1.4 秒；这 1.4 秒里剪贴板锁一直被占着，你自己按 Ctrl+C 时还要排队（正是"复制偶尔失效"的温床）。

两处修：

1. **前台换人就别等了** —— 轮询里加判断：前台已不是目标进程，这次复核拿到的只会是别人的剪贴板，立刻收手；
2. **记住"这个窗口不响应"5 秒** —— 不同程序不会在 100ms 内从不响应变成响应，直接跳过，不再空等。

## 二、在微信这类窗口划词"毫无反应"，现在会告诉你怎么办

日志统计（360 次取词）：`没拿到文字` **216 次**，其中 **53 次是真划了一段（>30px）**。看链路很清楚：

```
capture: UIA 读不到选区（该程序没有 UIA 文本模式）—— 常规流程不走 OCR 兜底
capture(exact): 700ms 内没读到新内容（写没写=false）
confirm: 复制通道没拿到文字，且「没取到文字就不弹」开着 —— 不弹
```

微信 4.x（Qt5）这类窗口三件事同时成立：没有 UIA 文本模式、忽略合成 Ctrl+C、而"常规划词不调 OCR"是**你 2026-10-30 的明确口径**（慢且不稳）——所以划词什么都不发生。

这不是 bug，是设计内取舍，**我没有去改它**。但"毫无反馈"会让人以为软件坏了，所以第一次遇到这种窗口会弹一条系统提示：

> 这个窗口读不到选区（不支持系统无障碍文本）。想识别它的文字：按 **Ctrl+Alt+O** 截图识别

每个程序只提示一次，不打扰。
