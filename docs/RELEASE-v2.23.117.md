# Quick Achieve v2.23.117

> 用户报的核心问题：**设置里明明打开了「开机自动启动」，重启后却没有启动。**
> 顺着这条线还查出三处「看起来正常、实际在空转」的地方，一起修了。

## 一、开机自启：为什么开了却不启动

### 旧实现的三个结构性问题

1. **启动自检被编译开关整段跳过**

   `main` 里写的是：

   ```rust
   if cfg0.auto_start && !env_on("QS_SKIP_AUTOSTART") && !QS_LITE_PORTABLE {
       win::set_autostart(true);
   }
   ```

   而本仓库的构建正是 `QS_LITE_PORTABLE = true` —— 于是这句话**从来没执行过**。
   设置页那个开关只在被点的那一下写一次注册表，之后：

   - 被「优化 / 安全」软件删掉 → 没人修；
   - 被另一份副本（旧 exe、桌面上的测试副本）顶掉 → 没人修；
   - 被任务管理器「启动」页禁用 → 程序自己看不出来。

2. **写完不校验**

   `RegSetValueExW` 返回 0 就当成功。组策略、安全软件、注册表重定向都可能让
   写入落空 —— 而设置页永远显示"开"，用户只能等下次开机才发现。

3. **提权与 Run 项打架**

   程序默认以管理员运行，而 `HKCU\...\Run` 只能拉起**普通权限**的实例，
   起来之后还要 `ShellExecuteW("runas")` 二次提权。开机那一刻这一跳可能被
   UAC 拦住（尤其用户不在电脑前）、被安全软件打断 —— 表现就是"没自启"。

### 现在的设计（新增 `src/autostart.rs`）

| 场景 | 落地方式 |
|---|---|
| 需要提权（默认） | **计划任务**：`ONLOGON` + `HIGHEST` + `/IT`，登录即以管理员启动，**一次 UAC 都不弹** |
| 不需要提权 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 的 `QuickAchieve` 值 |

- **写完立刻读回校验**：值真的在、且指向**这一份** exe（计划任务还要核对
  `<Command>`/`<Arguments>`），不通过就如实报错；
- **每次启动自检并修复一次**：

  ```
  autostart: 启动自检发现状态不对（未生效：启动项不存在），重写
  autostart: 开启 — 已生效：计划任务（登录时以最高权限运行，无 UAC）
  autostart: 当前状态 — 已生效：计划任务
  ```

- 识别「任务管理器 → 启动」里的停用状态（`StartupApproved\Run` 首字节 3），
  打开开关时顺手清掉这个标记；
- **绝不误删另一份副本的启动项**：只清"指向自己"或"指向已不存在文件"的项；
  带 `QS_INSTANCE_TAG` 的测试实例完全不碰别人的启动项：自测时一份临时实例用
  默认配置启动，把正式版的 Run 项当"残留"删了 —— 这条规则现在有单测钉住；
- 切换「默认以管理员身份运行」时**同时切换落地方式**：开 → 建任务、删 Run 项；
  关 → 删任务、写 Run 项（否则关掉提权开关后开机照样以管理员启动）。

### 界面与诊断

- 开关下面那行不再是死文案，而是后端的真实状态：

  ```
  已生效：计划任务（登录即以管理员启动，不弹 UAC）
  ⚠ 没生效：启动项指向别处（"C:\old\QuickAchieve.exe"）   [立即修复] · [在系统设置里查看]
  ```

- 新增命令：`autostart_state`（现查）、`autostart_repair`（按配置重写并回显结果）、
  `autostart_open_settings`（打开 Windows 的启动项页）；
- 「一键诊断」新增四项：配置/实际状态、`Run` 值原文、是否被系统禁用、计划任务。

### 开机拉起时的两个细节

- 自启命令固定带 `--autostart`：日志里能分清"开机拉起"与"用户双击"
  （`=== start, args=[…], boot=yes ===`）；提权重启时用原子量 `win::BOOT_START`
  把这个事实带过去 —— 不再改进程环境块（`set_var` 与别的线程 `env::var` 是竞争）；
- **先等 shell 就绪再建窗**（最多 10 秒）：登录那一刻 Explorer 还没把
  `Shell_TrayWnd` 建出来，`Shell_NotifyIcon` 会静默失败，图标进了虚空 ——
  用户看到的也是"没启动"。

## 二、备份轮转：每次保存都重解密全部旧备份

日志里能抓到同一批 20 多份 `config.auto(...)` 被反复「已解开」：

```
config: …config.auto(2026-11-05 13-14-46).QuickAchieve 是加密备份，已解开（完整度 170）
config: 保留旧备份 config.auto(2026-11-05 13-14-46).QuickAchieve（完整度 170 > 本次 155）
…（20 多行，每次保存重来一遍）
```

- 轮转要给每份旧备份算完整度（= 解密 + 解析），而"比本次更有价值的备份不删"
  让份数长期高于上限 → **每次保存**都要整批重新解密；
- 更糟的是只保护、不封顶：每保存一次 +1 份、受保护的一份都不删，
  备份目录**无限增长**。

修复：

- 完整度查询加**进程内缓存**（键 = 路径 + mtime + 大小 + 密码摘要），
  一份文件一次会话只解密一次；
- 普通备份仍按 `MAX_ROLLING = 8` 轮转；受保护的另算，但加**硬上限 40**：
  超过就按时间删最旧的并写日志。数据安全与"目录不会失控"两头都要。

## 三、设置页每改一项就请求一次 GitHub 额度

`fillAbout()` 每次配置广播都会调 `refreshGithubRate()`，而配置广播很频繁
（拖一下收藏面板尺寸就是一次）—— 每改一个设置就往 GitHub 打一个 `/rate_limit`。

修复：额度查询加 60 秒节流；用户主动操作（保存 / 清空令牌、检查更新）传
`force = true` 立刻刷新。

## 四、日志时间戳变成人话

旧：`[SystemTime { intervals: 134390073465027177 }] === start ===`
新：`[2026-11-13 10:10:24.456] === start, args=[…], boot=yes ===`

`tools/` 里解析日志的脚本（verify-delay / select-bar-probe / r77-img-speed /
round33-diag / run-ocr-parallel-e2e）都已兼容新旧两种格式。

## 五、`cargo test` 并行跑会偶发整进程崩溃

默认并行跑 485 条测试时随机得到 `STATUS_HEAP_CORRUPTION (0xC0000374)`：

- 根因：测试动的是**进程级共享资源** —— 剪贴板（全机器单例）、
  以及用 `std::env::set_var("QS_DATA_DIR"/"APPDATA")` 重定向数据目录。
  后者与别的线程里的 `env::var`（日志线程读数据目录）是一对真实的数据竞争；
- 修复：`.cargo/config.toml` 固定 `RUST_TEST_THREADS = "1"`，本地与 CI 一致；
- 顺手加固「智能直达一次开门读全」测试：外部剪贴板监视器改写内容时重试 3 次。
